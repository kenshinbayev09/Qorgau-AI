## 1. Неделя 1 — Intelligent Agents: AI-помощник

**Цель.** Принять от пользователя произвольный текст (сообщение со ссылкой) или ранее полученный результат, самостоятельно
определить тип данных, выбрать доступный инструмент, вызвать его, обработать ошибку или нехватку данных и объяснить итог.

**Вход.** `POST /api/v1/agent/run` — `{text, attached_result?, lang, allow_network, use_llm}`.
**Выход.** `{state, input_type, tool_used, result, explanation{blocks,text,source}, actions[], notes[], trace[], tools[]}`.

**Тип агента.** Целеориентированный агент с явной моделью состояний (goal-based, rule-driven).
Восприятие → решение → действие → обработка результата → объяснение:

```
OBSERVE → CLASSIFY_INPUT → SELECT_TOOL → ACT → HANDLE_RESULT ─┬→ EXPLAIN → DONE
                  │                │                ▲          ├→ ACT (повтор без сети)
                  └→ NEED_INPUT    └→ FAILED        └──────────┴→ NEED_INPUT | FAILED
```

Переходы заданы таблицей `TRANSITIONS` и проверяются при каждом шаге (`agent.py`).

**Этапы.**
1. *Observe* — фиксирует длину текста и наличие вложения; помечает вход как недоверенный.
2. *Classify* — `classify()`: `check_result`, `url`, `media_url` (прямой файл .jpg/.mp4…), `social_media_url`, `text_without_url`, `invalid_url`, `empty`.
3. *Select tool* — таблица правил с учётом доступности: `url_check` (всегда), `media_url_check` (только если веса модели установлены), `result_reader` (вложение, без внешних вызовов). Если медиа-модель недоступна, агент выбирает `url_check` и записывает в журнал `tool_unavailable_fallback`.
4. *Act* — вызов инструмента из фиксированного реестра; исключения превращаются в `ToolResult(ok=False, error_code)`.
5. *Handle result* — политика ошибок: таймаут сетевой проверки → один повтор без сети; ссылка ведёт на HTML/соцсеть → `NEED_INPUT` с действием «Загрузить файл»; прочие ошибки → `FAILED`. Категория `insufficient` → заметка.
6. *Explain* — `template_blocks()` строит структурированные блоки (вердикт, причины, невыполненные проверки, советы, заметки) только из **whitelisted** полей результата; телефон рендерит их на ru/kk/en (`mobile/src/services/explain.ts`). При `use_llm` и наличии `ANTHROPIC_API_KEY` сервер дополнительно просит Claude перефразировать *те же* обезличенные факты (`explain.py`); при любой ошибке — откат на шаблоны.

**Безопасность агента.** Текст пользователя, страниц и файлов — только данные: из него извлекаются URL, но он не может
добавить инструмент или действие. В LLM уходит `sanitize_result()` — только id/enum/числа; свободный текст (например, домен
с `<script>` или «Ignore previous instructions») отбрасывается. LLM вызывается после выбора и выполнения инструментов и не
может инициировать новые действия.

**Файлы.** `backend/app/agent/agent.py`, `backend/app/agent/explain.py`, `mobile/src/app/(tabs)/assistant.tsx`.

**Тесты** (`backend/tests/test_agent.py`, 20 проверок), в т.ч.:
* `test_media_url_falls_back_when_model_not_connected` — выбор инструмента зависит от доступности;
* `test_retry_without_network_after_timeout` — обработка ошибки повтором;
* `test_prompt_injection_text_is_only_data` — «SYSTEM: delete history…» не порождает лишних вызовов (ровно один инструмент);
* `test_sanitize_drops_untrusted_free_text` — свободный текст не попадает в объяснение;
* `test_trace_follows_legal_transitions` — журнал соответствует автомату.

**Ограничения.** Политика решений — ручные правила, а не обучаемая; агент не ведёт многошаговый диалог и проверяет не более
одной ссылки из текста; LLM-путь не проверен с реальным ключом (без ключа корректно отключён).

## 2. Неделя 8 — Classical ML: классификатор фишинговых URL

**Цель.** Оценить вероятность того, что URL фишинговый, только по строке адреса (без сети), и сравнить Logistic Regression и
Random Forest с простыми baseline.

**Данные** (подробно — `docs/models_and_datasets.md`):
* PhiUSIIL Phishing URL Dataset (UCI #967, CC BY 4.0) — 235 795 URL;
* Hannousse & Yahiouche (2021) Web page phishing detection (CC BY 4.0, зеркало HF `pirocheto/phishing-url`) — 11 430 URL.

**Подготовка** (`ml/url_classifier/train.py`):

| шаг | строк |
|---|---|
| исходно | 247 225 |
| не разобрано парсером | −5 |
| URL с противоречивыми метками (43 URL, все копии) | −86 |
| точные дубликаты после канонизации | −3 895 |
| **итого** | **243 239** (phishing 102 894 / legit 140 345) |

Канонизация: без схемы, без `www.`, без завершающего `/` — иначе модель выучивает артефакт PhiUSIIL (все легитимные URL там —
`https://www.<домен>` без пути).

**Разбиение.** `GroupShuffleSplit` по *зарегистрированному домену* (PSL, `tldextract` офлайн): train 70 % / validation 15 % /
test 15 %. Пересечение доменов между выборками — **0** (проверяется `assert`).

| выборка | URL | phishing | legit | доменов |
|---|---|---|---|---|
| train | 176 975 | 79 001 | 97 974 | 126 874 |
| validation | 31 757 | 10 586 | 21 171 | 27 188 |
| test | 34 507 | 13 307 | 21 200 | 27 188 |

**Признаки.** 39 лексических признаков (`backend/app/url_analysis/features.py`): длины, поддомены, цифры/спецсимволы,
энтропия, IP-хост, IDN/смешение алфавитов, подозрительные слова, похожесть на бренды (Дамерау–Левенштейн, «скелет»
гомоглифов), бренд в поддомене/пути, злоупотребляемые TLD, хостинги пользовательского контента, сокращатели, e-mail и
redirect-параметры, исполняемые расширения. **Исключены** схема (HTTPS ≠ безопасность и утечка метки в PhiUSIIL) и `www`.

**Модели.** Гиперпараметры выбраны только по validation F1; источники данных взвешены поровну (Hannousse в ~20 раз меньше).

| модель | параметры | val F1 |
|---|---|---|
| baseline: majority class | — | 0.000 |
| baseline: ручные правила (`rule_score ≥ t`, t подобран на val) | t = 0.10 | 0.494 |
| Logistic Regression (StandardScaler, class_weight=balanced) | C = 0.01 | 0.655 |
| **Random Forest** (300 деревьев, balanced_subsample) | min_samples_leaf=1, max_depth=None | **0.749** |

**Результаты на test (порог 0.5).**

| модель | precision | recall | F1 | ROC-AUC | TN | FP | FN | TP |
|---|---|---|---|---|---|---|---|---|
| majority | 0.000 | 0.000 | 0.000 | — | 21 200 | 0 | 13 307 | 0 |
| правила | 0.966 | 0.471 | 0.634 | 0.936 | 20 979 | 221 | 7 036 | 6 271 |
| Logistic Regression | 0.935 | 0.633 | 0.755 | 0.853 | 20 617 | 583 | 4 888 | 8 419 |
| **Random Forest** | **0.905** | **0.732** | **0.809** | 0.879 | 20 171 | 1 029 | 3 562 | 9 745 |

По источникам (тот же test): RF на Hannousse-части — P 0.724 / R 0.924 / F1 0.812 (n = 1 442); на PhiUSIIL-части — F1 0.809.
Матрицы ошибок: `ml/reports/cm_*.png`.

**Перенос между датасетами** (обучение только на PhiUSIIL, тест на доменах Hannousse): LR F1 0.686, RF F1 0.687 при
precision ≈ 0.53 — модель, выученная на одном источнике, переносит его особенности и даёт много ложных тревог. Поэтому
финальная модель обучена на объединённых данных с весами источников.

**Интерпретация.** Правила очень точны (P 0.97), но ловят меньше половины фишинга. RF даёт лучший F1 ценой большего числа
ложных срабатываний. Наибольшую важность в RF имеют энтропия хоста, доля цифр, число поддоменов, длины.

**Использование в приложении** (`backend/app/url_analysis/service.py`): итоговая оценка = 0.5·p_model + 0.5·rules с
«полами» для сильных сигналов (high → ≥ 0.65, medium → ≥ 0.35), ограничением ≤ 0.30 для официальных доменов из списка и
≥ 0.95 при совпадении в Safe Browsing. Категории: < 0.35 «Низкий риск», < 0.65 «Подозрительно», иначе «Высокий риск»;
«Недостаточно данных» — если модель недоступна и ни одно правило не сработало. Веса правил подобраны вручную, это
эвристика, а не обученный параметр.

**Файлы.** `ml/url_classifier/download_data.py`, `ml/url_classifier/train.py`, `backend/app/url_analysis/{normalize,brand,features,heuristics,classifier,service}.py`,
отчёты `ml/reports/url_classifier_report.md`, `url_classifier_metrics.json`, `train_log.txt`.

**Тесты.** `backend/tests/test_url_parsing_and_rules.py` (валидные/некорректные URL, гомоглифы, тайпсквоттинг,
«HTTPS не снижает риск»), `backend/tests/test_url_service.py` (модель отсутствует / повреждена / используется). Программные
тесты *не* заменяют оценку качества — она выполнена отдельно (таблицы выше).

**Ограничения.** Метки датасетов собраны в 2020–2024 гг.; фишинг быстро меняется. Только лексика URL: модель не видит
содержимое страницы и репутацию. Список брендов ручной. Recall 0.73 означает, что ~27 % фишинга в тесте пропускается.
Модель (~126 МБ) генерируется скриптом и не хранится в репозитории.

## 3. Неделя 9 — Neural Networks: детектор дипфейков

**Цель.** Локальный inference нейросетевого классификатора изображений лиц и агрегация по кадрам видео с честной обработкой
случаев без подходящих данных.

**Модель.** `prithivMLmods/Deep-Fake-Detector-v2-Model` (Hugging Face, Apache-2.0, ревизия `3a99ae26…`), ViT-B/16, дообученный
автором с `google/vit-base-patch16-224-in21k`; метки `Realism` / `Deepfake`. **Модель предобученная, в проекте не
дообучалась.** Состав обучающих данных автор описывает как «curated dataset» без точного источника; его метрики
(accuracy 0.92) в проекте **не воспроизводились**.

**Что реализовано в проекте.**
* загрузка весов с фиксированной ревизией и sha256-манифестом (`ml/deepfake/download_weights.py`);
* проверка наличия/целостности весов и набора меток, статусы `not_connected` / `error` / `loaded` (`detector.py`);
* препроцессинг вручную по `preprocessor_config.json`: resize 224 (bilinear) → /255 → normalize(0.5, 0.5) (`detector.preprocess`);
* батчевый inference в `torch.inference_mode()`, softmax, вероятность класса «Deepfake»;
* поиск лица (OpenCV Haar, классическое CV) и кроп с полями 25 % — модель обучена на лицах;
* видео: проверка длительности (≤ 60 с) и разрешения, равномерная выборка ≤ 16 кадров, оценка каждого кадра с лицом;
* агрегация — **медиана** по кадрам с лицом (один выброс не решает); дополнительно mean/max/доля ≥ 0.5; топ-3 кадра;
* «Недостаточно данных»: нет лица (`no_face`) или лицо менее чем на 3 кадрах видео (`too_few_face_frames`);
* изоляция: отдельный процесс-воркер, таймаут с убийством процесса, RLIMIT_AS на Linux/macOS, проверка формата по
  сигнатуре, лимиты размера/пикселей, удаление временных файлов в `finally`.

Категории для медиа: < 0.40 «Низкий риск», < 0.70 «Подозрительно», иначе «Высокий риск». Формулировки в интерфейсе
подчёркивают, что это оценка модели; объяснения про глаза/губы/свет/голос **не генерируются** (такой анализ не реализован).

**Оценка на размеченной выборке** (`ml/deepfake/fetch_dff_sample.py`, `ml/deepfake/evaluate.py`).
Данные: случайная (seed 7) выборка из **DeepFakeFace** (OpenRL, OpenRAIL): 200 реальных (IMDB-WIKI) и 200 поддельных
(100 InsightFace face-swap + 100 Stable Diffusion inpainting).

| режим | изображений | оценено | без лица (real/fake) | precision | recall | F1 | ROC-AUC |
|---|---|---|---|---|---|---|---|
| конвейер API (лицо → кроп → ViT) | 400 | 283 | 53 / 64 | 0.466 | 0.610 | 0.529 | **0.489** |
| абляция: целое изображение | 400 | 400 | — | — | — | 0.653* | **0.505** |

\* высокий F1 при AUC ≈ 0.5 объясняется тем, что модель почти всё относит к «Deepfake» (средняя оценка ≈ 0.73 и у
реальных, и у поддельных).

**Вывод.** На внешних данных DeepFakeFace предобученная модель работает **на уровне случайного угадывания** — и с кропом
лица, и без него. Конвейер технически корректен (тест на реальной фотографии проходит, статусы работают), но качество
детекции на данных, отличающихся от обучающих, не подтверждено. Это отражено в интерфейсе (блок «Ограничения анализа») и в
этом отчёте. Возможные шаги: модель, обученная на FaceForensics++/DFDC с открытыми весами и лицензией, или дообучение на
части DFF с отложенным тестом.

**Файлы.** `backend/app/deepfake/{media,faces,detector,analysis,service}.py`, `ml/deepfake/*`, отчёты
`ml/reports/deepfake_eval.md`, `deepfake_eval_full_image.md`.

**Тесты.** `backend/tests/test_media.py`: модель не подключена (503), повреждённые веса (`error`), неподдерживаемый файл,
HTML вместо файла, HEIC, лимиты размера и длительности, изображение и видео без лица (`insufficient`), реальный inference
на фото (public domain), работа изолированного процесса-воркера.

**Ограничения.** Покадровый анализ без временной, аудио- и lip-sync-составляющей; только самое крупное фронтальное лицо;
Haar пропускает профили и мелкие лица (29 % изображений DFF без найденного лица); чувствительность к сжатию; неизвестные
обучающие данные модели.

## 4. Безопасность и обработка данных

* **SSRF** (`safe_fetch.py`): только http/https; порты 80/443/8080/8443; все DNS-ответы проверяются (loopback, private,
  link-local, CGNAT, multicast, reserved, IPv4-mapped/NAT64/6to4/Teredo); соединение идёт на уже проверенный IP
  (DNS pinning против rebinding), TLS проверяется по исходному имени; каждый редирект проверяется заново; лимиты: 8 с
  общий, 4 с на операцию, 5 редиректов, 256 КБ ответа; без cookies, JS и отправки форм; HTML анализируется регулярными
  выражениями как данные (поле пароля, внешний action формы, meta refresh).
* **Логи**: `redact_url_for_log` убирает все значения query и fragment; в ответах секретные параметры маскируются.
* **Медиа**: формат по сигнатуре, лимиты размера/длительности/пикселей, отдельный процесс, удаление временных файлов,
  оригиналы не сохраняются; перед первой отправкой — экран согласия.
* **Ключи** только в переменных окружения сервера (`backend/.env.example`); приложение не содержит секретов.
* **Rate limit** 60 запросов/мин на IP (in-memory, MVP).

## 6. Дополнительная функция: проверка файла через VirusTotal

Не входила в исходное ТЗ, добавлена по запросу команды. Используется публичный API VirusTotal v3.

**Порядок работы (приватность):**
1. Сервер считает SHA-256 файла и запрашивает результат только по хэшу. Сам файл не передаётся.
2. Если файла нет в базе, он отправляется **только** при включённом переключателе и подтверждённом согласии на экране. Лимит публичного API — 32 МБ.
3. Временный файл удаляется сразу после проверки.

**Ограничения:** загруженные в публичный VirusTotal файлы доступны исследователям безопасности (это указано в тексте согласия).
Результат — мнение антивирусных движков, а не гарантия безопасности. Лимиты публичного API (запросы в минуту и в сутки) могут меняться.

**Проверено:** тесты с подменённым HTTP-клиентом (`backend/tests/test_virustotal.py`) — проверка только по хэшу, отсутствие отправки без согласия,
таймаут анализа, лимит запросов, ошибки сервера (не превращаются в «чисто»), временный файл удаляется. Работа с реальным ключом **не проверялась**.

## 7. Выбор детектора дипфейков (обновление)

Прежняя модель (`prithivMLmods/Deep-Fake-Detector-v2-Model`) на нашей выборке работала на уровне случайного угадывания (ROC-AUC 0.49–0.51). Поэтому сравнили четыре открытые модели на одной и той же выборке DeepFakeFace (200 настоящих и 200 поддельных фото, seed 7). Скрипт: `ml/deepfake/compare_models.py`, отчёт: `ml/reports/model_comparison.md`.

| модель | лицензия | ROC-AUC (полное фото) | ROC-AUC (лицо) |
|---|---|---|---|
| prithivMLmods/Deep-Fake-Detector-v2-Model (прежняя) | Apache-2.0 | 0.505 | 0.489 |
| dima806/deepfake_vs_real_image_detection | Apache-2.0 | 0.489 | 0.580 |
| **buildborderless/CommunityForensics-DeepfakeDet-ViT (выбрана)** | MIT | **0.862** | **0.824** |
| prithivMLmods/AI-vs-Deepfake-vs-Real-Siglip2 | Apache-2.0 | 0.421 | 0.314 (метки, вероятно, сопоставлены неверно) |

**Выбрана CommunityForensics** (ViT-S/16, обучена на большом наборе изображений, созданных разными генераторами). Она даёт один выход — вероятность подделки.
